# 提现人工审核队列 + 多签复核

> 资金安全第一梯队第 3 项。将提现审核从"单步审批直接上链"升级为**两阶段人工审核（初审 + 复核）**，
> 复核须由与初审不同的审核员执行，契合金融系统的"不相容职责分离(SoD)"与人工风控复核要求。

## 审核状态机（t_withdraw.status）

```
0=待审核 → [初审通过] → 8=初审通过待复核
             │                    │
             │[初审拒绝]          ├─ [复核通过] → 2=处理中(冻结+上链; 若超冷阈值则转6=待冷签)
             ▼                    │
            4=拒绝                └─ [复核拒绝] → 4=拒绝
```

| 状态 | 含义 |
|------|------|
| 0 | 待审核 |
| 1 | 审核中 |
| 2 | 处理中（已冻结上链） |
| 3 | 成功 |
| 4 | 拒绝 |
| 5 | 失败回滚 |
| 6 | 待冷钱包签名（前项冷钱包流程） |
| 7 | 冷签名完成待广播 |
| 8 | **初审通过待复核**（新增） |

## 接口（AuditRequest 扩展）

```json
{
  "approve": true,
  "level": 1,          // 1=初审(默认), 2=复核
  "reviewer": "admin1",// 审核员标识(必填)
  "remark": "初审通过"
}
```

- **初审**(level=1, approve)：`0/1 → 8`（待复核），不冻结不上链
- **复核**(level=2, approve)：`8 → 2`（冻结+上链）或转冷签；reject → 4
- **安全约束**：复核人 `!=` 初审人（同一审核员不可既审又复），否则拒绝

## 验证（mock-rpc + 本地 chain）

- ✅ 初审通过 → `status=8, auditBy=admin1`
- ✅ 复核用**同一审核员** → 拒绝"复核人不能与初审为同一审核员"
- ✅ 复核用**不同审核员** → 进入冻结+上链路径（冻结冲突为测试幂等数据问题，非复核逻辑）

## 与冷钱包的多签衔接

- 复核通过后若金额 ≥ 冷阈值 → 转**冷钱包待签**(status=6)，再走离线签名 + 多签（前项实现）
- 即：**初审 → 复核 → （大额）冷钱包多签/（小额）热钱包广播**，全链路人工 + 离线控制

## 生产进一步强化（可选）

1. **角色权限**：初审/复核绑定 RBAC 角色，管理平台(admin)按角色分配
2. **额度限额**：超限提现强制走复核 + 多签；按币种/单笔/日累计限额
3. **不可抵赖**：审核记录入库审计 + 操作者 IP/痕迹，配合撮合审计链
4. **超时升级**：待复核超时(N小时)自动升级到更高权限或人工催办
